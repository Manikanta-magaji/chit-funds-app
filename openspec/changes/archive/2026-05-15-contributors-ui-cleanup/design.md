## Context

The Contributors tab in `GroupDashboardPage.tsx` renders each `ContributorSlot` with a cluster of badges: registration status, payment status (paid / unpaid), winner indicator, and — for admin users without a slot — a generic "User #N" label generated by the backend. The `InstallmentPanel` component uses `statusBadgeClass()` to map `"pending"` and `"partial"` to distinct badge colours, but the visual difference is lost on non-technical users.

All changes are confined to the frontend; the backend API, data model, and enum values remain untouched.

## Goals / Non-Goals

**Goals:**
- Remove paid/unpaid status badges from Contributor slot rows (Contributors tab only).
- Replace the "🏆 Winner" text badge with a lone `🏆` icon inline with the slot name.
- Show admins who hold no contributor slot with their real `display_name` and a muted "Admin only" tag instead of "User #N".
- Merge the `pending` and `partial` installment badge labels into a single **"In Progress"** display label (badge colour unified to warning/yellow).

**Non-Goals:**
- No backend changes (API, models, enums remain identical).
- No changes to the Overview tab's Installment Tracking panel logic.
- No redesign of the Contributors tab layout beyond the items listed above.

## Decisions

### 1. Remove payment status from Contributors tab

**Decision:** Strip paid/unpaid badge rendering from contributor slot rows entirely.

**Rationale:** Payment status is authoritative in the Installment Tracking panel on the Overview tab. Duplicating it on Contributors creates two sources of visual truth that can appear out of sync (e.g., during a mutation). Removing it from Contributors keeps each tab focused on a single concern.

**Alternative considered:** Keep the badge but grey it out. Rejected — greyed badges still add visual noise and confuse users about their meaning.

### 2. Winner indicator: icon only

**Decision:** Replace `<span className="badge badge-winner">🏆 Winner</span>` with an inline `🏆` icon placed immediately after the slot name, with a tooltip `title="Prize winner this cycle"`.

**Rationale:** The icon alone is immediately recognisable; the text label "Winner" is redundant. Removing it reduces badge clutter without losing information.

### 3. Admin-only users display

**Decision:** In the Contributors tab, identify admin users who are not linked to any slot by querying `group.admin_ids` against the slot list. For each such admin, render a read-only row showing their `display_name` and a muted "Admin" label.

**Rationale:** The current backend-generated "User #N" placeholder leaks an internal surrogate identity to all group members. Showing the actual name with a clear role label is more transparent and useful.

**Implementation note:** The `GroupDashboardPage` already holds the `group.admin_ids` array and the list of linked users from `slots`. We fetch admin profiles for admins not in any slot — these users are already loaded via the admin management section. We can reuse the `adminUsers` data already in scope (if present) or add a small targeted query.

### 4. Unify `pending` and `partial` badge labels

**Decision:** In `InstallmentPanel.tsx`, map both `"pending"` and `"partial"` status strings to the label **"In Progress"** with `badge-warning` styling, while keeping `"paid"` and `"unpaid"` as-is.

**Rationale:**
- `partial` (some sub-members paid) and `pending` (awaiting admin confirmation) both mean the slot has not yet completed payment. From the user's perspective they are interchangeable intermediate states.
- The sub-member expansion rows already show individual sub-member statuses, so the granular `partial` distinction is redundant at the slot level.
- `pending` still exists functionally (self-report workflow) so the enum is preserved; only the displayed label changes.

## Risks / Trade-offs

- **Admin user data availability:** Admin users not in any slot may not have their profiles pre-loaded. We need to ensure we can resolve their `display_name`. The admin management section already fetches admin user data — we can reuse that or rely on `group.admin_ids` plus a lightweight lookup. [Risk: extra fetch for edge-case admins] → Mitigation: Render name from any already-loaded source; fall back to "Admin" label if display name is unavailable.
- **"In Progress" label scope:** Merging `pending` and `partial` means an admin sees less specificity at the slot level. [Risk: admin cannot immediately tell self-reported vs partial sub-member payment] → Mitigation: The expanded sub-member rows still show exact per-sub-member statuses, and admins can use the confirm-payment UI for pending items.
